# Brewing implementation plan

Implement the approved [brewing contract](../specs/2026-10-19-brewing.md) through the existing native recipe provider. Follow [AGENTS.md](../../AGENTS.md): no formatting tools, existing style, immediate per-step commits generated with `$commit-message`.

1. Record the pinned Minecraft 1.21.1 / NeoForge 21.1.202 brewing access, precedence and batch semantics under `docs/research/`. Read the applicable specification and this plan before implementation.
2. One Luna worker owns the production and regression files. Add meaningful failing brewing tests using existing bootstrap/recipe-reader conventions. Stop for the parent to commit the test step and run the focused tests to observe RED.
3. Add a package-local native brewing reader, integrating discovery, fresh evidence resolution and bounded planner candidates through `NativeRecipeReader` and `NativeProvider`. Reuse the existing payload representation with only necessary visibility changes; do not add a public API, registry or general decoder framework. Parent commits the implementation before running checks.
4. Run focused tests, handle failures in separate committed fix steps, and review the implementation against component identity, live pagination, opaque custom behavior, precedence and shared-batch limits.
5. Run Java 21 `gradlew.bat test build`. Record actual test counts, the built artifact and the absence of installed acceptance under `docs/validation/`; add player-facing checks under `docs/testing/` without assigning automated commands to the player.
6. Update the roadmap and changelog, obtain a bounded code review, resolve material findings and finish with `git diff --check`. No formatter, merge, push, instance installation or desktop automation is part of this task.

Follow-up: after the player installed and requested live checks on 2026-10-19, the agent drove the installed client. The [validation record](../validation/2026-10-19-brewing.md) separates passing focused reader checks from the failed ordinary-question discovery, planner batch-count ambiguity and untested custom/physical behavior. The original implementation scope above did not include this later authorization.
