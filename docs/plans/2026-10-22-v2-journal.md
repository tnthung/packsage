# v2 Journal and Notes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Record what happens in a singleplayer world into a per-world SQLite journal without touching the game thread's frame or tick time, let the model search it, and let the model keep the player's own reports as notes that it saves, updates and deletes without being asked.

**Architecture:**
- **Package.** Everything new lives in `dev.packsage.journal`, so Stages 1–3 can keep editing `WorldTools`, `PackSageTools` and `GroundingInstructions` without conflicts here.
- **Recording.**
  - Pure parts: event records, run merging, the bounded queue, position packing, trackers and recording rules.
  - Thin NeoForge hooks (`JournalHooks`) extract plain data on the server thread and only push it onto the queue.
  - A background writer thread owns the SQLite connection. It drains the queue about once a second, merges runs and writes one WAL transaction per batch.
- **Notes.** Notes live in the same database. They are mirrored in memory, so navigation and `Anchor.OfNote` never wait on disk.
- **Provider.** A new `KnowledgeProvider`, `JournalTools`, with provider id `journal`, exposes `search_journal`, `remember`, `update_note` and `forget_note`. It owns the `journal-place|…` and `journal-note|…` highlight links.
- **Additive edits elsewhere.**
  - `Anchor` gains `OfNote`, and `WorldTools` resolves it.
  - `Toolbox.Context` gains the originating chat message.
  - The prompt gains one minimal rule.

**Tech Stack:** Java 21, NeoForge 21.1.202 / Minecraft 1.21.1, JUnit 5, `org.xerial:sqlite-jdbc` 3.46.x bundled jar-in-jar.

## Global Constraints

- **Singleplayer only.** Recording runs only on the integrated server (`client.getSingleplayerServer()`), including when the world is open to LAN, where it records every player. Without an integrated server, every journal tool fails `UNAVAILABLE`.
- **The game thread never waits on disk, the database or the model.** Server-thread hooks only copy plain data and call `EventQueue.offer`, which never blocks. Opening, writing, flushing and closing the database happen only on the `packsage-journal` writer thread. Queries run on the `packsage-worker` executor. Navigation and anchors read the in-memory `NoteBook` only.
- **Run merging** (spec, exact): consecutive events with the same actor, action, subject and dimension, less than 5 seconds apart and within 16 blocks of the run's bounding box, become one row. That row has a count, a time span, a bounding box and the packed exact positions. Container transfers and explosions merge the same way.
  - "5 seconds" is `gameTime - run.lastGameTime < 100` ticks.
  - "Within 16 blocks of the box" means inside the box grown by 16 on every axis.
- **Overflow.** A full queue folds events into count-only rows. It never blocks, and never silently drops an event without counting it.
- **Writer cadence.** The writer drains about once a second (`PERIOD_MILLIS = 1000`) and writes one SQLite transaction per batch in WAL mode. It flushes when the world closes.
- **Database path:** `saves/<world>/packsage/journal.db`, which is `server.getWorldPath(LevelResource.ROOT).resolve("packsage").resolve("journal.db")`. Everything is kept; there is no pruning.
- **Notes are what the player said.** Note records carry `"trust": "player-said"` and `Evidence.Authority.PLAYER_REPORTED`, and are never labelled as game-confirmed. Saving is invisible: no toast or chat line, and the prompt says not to announce it.
- **Coverage.** A result that cannot rule something out is `PARTIAL` and says why. Examples: overflow rows without positions, a time range that starts before recording, a gap in recording, or a failed batch.
- **Persistent links** follow the [persistent navigation contract](../specs/2026-10-18-persistent-navigation.md). `journal-note|<noteId>` resolves the note's current place when clicked. `journal-place|<dimension>|x,y,z` is the place itself.
- **Commits.** Commit each step as soon as it is written: failing tests are one commit, and the implementation another. Use `$commit-message` for every message (`[Add]`/`[Chg]`/`[Fix]`/`[Rmv]`), with no AI attribution. No formatting tools.
- **Start point.** Start from the branch after Stages 1–3 have merged. Re-read every shared file named in a task before editing it; line numbers will have moved, so this plan names symbols, not lines. Every edit outside `dev.packsage.journal` is an addition to a list, switch, record or constructor overload.

## Review Focus

1. **A run grows while the model pages through results** (the player keeps mining between two `search_journal` pages). Expect no entry repeated and none skipped. Entries sort by `first_wall`, which never changes when a run is extended. Test in Task 6.
2. **The player quits seconds after a burst** (a TNT chain, then Save and Quit to Title, or closing Minecraft). Expect every queued event and open run to be in the database on the next launch. Reopening the same world while the previous close is still flushing waits for it on the writer thread, never on the server thread. Tests in Tasks 5 and 9.
3. **A question about a time before the journal existed**, or a period played without PackSage. Expect `PARTIAL`, with `recordingSince` and the gap in the note, never "nothing happened". Test in Task 6.
4. **The database cannot be opened** (locked by a second Minecraft instance on a copied save, read-only folder, or a corrupt file). Expect the game to play normally, recording to be off with one log line, and the tools to fail `UNAVAILABLE` with the reason. Test in Task 9.
5. **A saved note link clicked after "I moved my iron farm" or after `forget_note`.** Expect the moved note to highlight its new place under the same target id. A forgotten note reports unavailable and draws nothing. A note in another dimension opens with its coordinates as text. Tests in Task 12.

### Schema v1 (decided here; Task 1 creates it)

```sql
PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; PRAGMA foreign_keys=ON;
CREATE TABLE meta(key TEXT PRIMARY KEY, value TEXT NOT NULL);
  -- schema_version=1, created_wall, created_game_time
CREATE TABLE sessions(id INTEGER PRIMARY KEY, started_wall INTEGER NOT NULL, started_game_time INTEGER NOT NULL,
  ended_wall INTEGER, ended_game_time INTEGER);
CREATE TABLE events(
  id INTEGER PRIMARY KEY, type TEXT NOT NULL, actor TEXT NOT NULL, subject TEXT, dimension TEXT NOT NULL, grp TEXT,
  count INTEGER NOT NULL, amount INTEGER NOT NULL,
  first_game_time INTEGER NOT NULL, last_game_time INTEGER NOT NULL, first_wall INTEGER NOT NULL, last_wall INTEGER NOT NULL,
  at_x INTEGER, at_y INTEGER, at_z INTEGER,                       -- first position; NULL for count-only rows
  min_x INTEGER, min_y INTEGER, min_z INTEGER, max_x INTEGER, max_y INTEGER, max_z INTEGER,
  positions BLOB,                                                 -- Positions.encode; NULL for count-only rows
  detail TEXT,                                                    -- compact JSON of the run's first event
  count_only INTEGER NOT NULL DEFAULT 0);
CREATE INDEX events_time ON events(first_wall);
CREATE INDEX events_dimension_time ON events(dimension, first_wall);
CREATE INDEX events_subject_time ON events(subject, first_wall);
CREATE INDEX events_type_time ON events(type, first_wall);
CREATE INDEX events_count_only_time ON events(first_wall) WHERE count_only = 1;
CREATE VIRTUAL TABLE events_box USING rtree_i32(id, min_x, max_x, min_y, max_y, min_z, max_z);
CREATE TABLE structure_visits(dimension TEXT NOT NULL, structure TEXT NOT NULL, start_chunk TEXT NOT NULL,
  PRIMARY KEY(dimension, structure, start_chunk));
CREATE TABLE notes(
  id TEXT PRIMARY KEY, text TEXT NOT NULL, player_words TEXT, tags TEXT NOT NULL,   -- tags: comma-joined, sorted
  dimension TEXT, x INTEGER, y INTEGER, z INTEGER,
  created_wall INTEGER NOT NULL, created_game_time INTEGER NOT NULL, updated_wall INTEGER NOT NULL,
  origin_conversation TEXT, origin_request TEXT);
CREATE INDEX notes_time ON notes(created_wall);
```

### Task 5: Background writer

**Files:**
- Modify: `JournalStore.java` (batch writes)
- Create: `JournalWriter.java`, `JournalStats.java` in `dev.packsage.journal`
- Test: `src/test/java/dev/packsage/journal/JournalWriterTest.java`

**Interfaces:**
- Consumes: `JournalStore` (Task 1), `RunMerger` (Task 3), `EventQueue` (Task 4).
- Produces:
  - `JournalStore.writeBatch(List<Run> changed, List<OverflowRow> overflow) throws SQLException`, in one transaction:
    - a run with `rowId < 0` is inserted into `events` and `events_box`, and the row id is set on the run;
    - otherwise the run's `events` and `events_box` rows are updated;
    - each overflow row is inserted with `count_only = 1`, null place, box and positions, and no `events_box` row;
    - a `STRUCTURE` run is inserted only when `INSERT OR IGNORE INTO structure_visits(dimension, subject, grp)` changed a row; otherwise it is skipped and keeps `rowId = -1`.

    `int transactions()` counts commits, for tests.
  - `final class JournalStats`, holding `LongAdder`/`AtomicLong` fields:
    - `offered`, `overflowed`, `written`, `failedEvents`;
    - `maxBatchMillis`, `maxHookNanosPerTick` and `hookNanos(long)`;
    - `String summary()`, logged through `PackSageLog` at close.
  - `final class JournalWriter`, with constructor `JournalWriter(Callable<JournalStore> opener, EventQueue queue, JournalStats stats, LongSupplier gameTime, LongSupplier wallClock, long periodMillis)`:
    - `void start()` starts the non-daemon thread `packsage-journal`, which first runs `opener` and `startSession`;
    - `CompletableFuture<JournalStore> ready()`;
    - `<T> CompletableFuture<T> submit(StoreCommand<T> command)`, where `interface StoreCommand<T> { T run(JournalStore store) throws SQLException; }`. Commands run on the writer thread as soon as it wakes, ahead of the next batch, and are used by notes.
    - `int drainOnce()` drains up to 65,536 events, merges them, calls `writeBatch(merger.takeChanged(), queue.drainOverflow())` and `merger.closeIdle(gameTime)`, and returns the number of events. It is package-private, so tests call it without the thread.
    - `CompletableFuture<Void> close()`, after which the thread does the following, in order:
      1. stops accepting commands;
      2. calls `queue.close()`;
      3. drains until empty;
      4. writes the remaining changed runs;
      5. ends the session;
      6. calls `store.close()`;
      7. completes the future.

      The future is never awaited on the server thread.

    - **`search_journal(filter, cursor?)`.** `filter` is required and may be `{}`. It may hold:
      - `time {after?, before?, lastMinutes?}`: `after` and `before` are ISO-8601 instants (`Instant.parse`), and `lastMinutes` is an integer from 1 to 5,256,000, never combined with `after`;
      - `area {center?, radius}`: `center` is an anchor, default player, and `radius` is an integer from 0 to 256;
      - `dimension?`, a resource id;
      - `types?`: the 16 event ids plus `note`;
      - `subjects?`: resource ids, up to 32;
      - `text?`, up to 256 characters;
      - `notesOnly?`.

      Cursors are opaque UUID tokens in a 256-entry LRU, bound to tool, arguments and scope, with the same rules as `WorldTools.cursor`. They map to the `JournalSearch` keyset.
    - **`remember(text, at?, tags?)`.** `at` is an anchor of type player, block or entity, and becomes the note's place. `tags` are up to 8 strings. The note gets a new id, `playerWords` from `context.origin()`, and its creation game time. It is written through `journal.write` and put in the `NoteBook`. The result is the note record plus a `possibleDuplicates` payload array (`NoteBook.similar(text, 3)`, excluding itself) with `id`, `text` and `place`.
    - **`update_note(id, text, at?, clearPlace?, tags?)`.** Supplying both `at` and `clearPlace: true` is `INVALID_ARGUMENTS`. An unknown id is `INVALID_ARGUMENTS` with the message "no note <id>; find it with search_journal notesOnly". The result is the updated note record.
    - **`forget_note(id)`.** It deletes the note, and returns no records with detail "note <id> forgotten".
  - **Event records:**
    - provider `journal`, handle `event:<id>`, kind `OTHER`;
    - `Authority.SERVER_READ`, `Activity.INACTIVE`, title from `RunSummary`;
    - payload: `type`, `actor`, `actorName?`, `subject`, `dimension`, `count`, `amount`, `from`, `to` (ISO), `fromGameTime`, `toGameTime`, `minutesAgo`, `at`, `box {min, max}`, `summary`, `detail` (parsed JSON), `countOnly`, and `inArea` / `inAreaCount` when area-filtered;
    - navigation target `journal-place|<at>` when `at` is present.
  - **Note records:**
    - handle `note:<id>`, kind `OTHER`, `Authority.PLAYER_REPORTED`;
    - payload: `type: "note"`, `id`, `text`, `playerWords`, `trust: "player-said"`, `tags`, `place?`, `created`, `updated`, `origin {conversation, request}`;
    - target `journal-note|<id>` when the note has a place.
  - `readEvidence` rereads `event:` and `note:` handles, using the `Toolbox.Context.reference` checks as `WorldTools` does.
  - Result coverage and detail come from `Page.coverage()` and `Page.note()`. The detail always starts with "recording since <ISO>".
  - Descriptions, stated in `PackSageTools`:
    - **`search_journal`:** "Search what this world's journal recorded since it began: blocks placed and broken (also by explosions), items put into or taken from containers, deaths with their cause, kills, dimension changes with the portal, advancements, villager profession changes, curing, conversion and trades, raids, first structure entries, explosions, and the player's notes. Filter by time, area around an anchor, dimension, types, subject ids and text. Newest first, 64 per page. Repeated similar events come back as one run with a count, time span and box. A result covers only the recording period it reports. Notes are what the player said, not facts the game confirmed."
    - **`remember`:** "Save a note when the player reports something they did, built, achieved or found. Pass their statement as text, at for the place they mean (the player for 'here'), and a few lowercase tags such as build, achievement or resource. If possibleDuplicates shows the same thing, update_note it instead. Save silently; mention notes only when the player asks."
    - **`update_note`:** "Correct a saved note when the player changes, moves or renames what they reported: replace its text, move it with at, clear its place or replace its tags. Find its id with search_journal notesOnly."
    - **`forget_note`:** "Delete a saved note when the player says it no longer applies or asks you to forget it."

## Open questions

These are decided as written above. Each needs confirmation before or during review.

1. **Separate provider id `journal`,** not `world`. This keeps `WorldTools` free of conflicts and gives journal links their own targets. The cost is one-line additions in `ScreenText`, `AssistantScreen` and `AssistantRuntime`. Recommendation: accept, matching the `progress` provider in Stage 2.
2. **Which types merge.** The spec's merge rule is general. This plan merges only place, break, deposit, withdraw, kill, trade and explosion. Deaths, conversions, profession changes, raids, structures, dimension changes and advancements stay one row each, so each keeps its own entity, cause and name. Recommendation: accept.
3. **Time basis for "5 seconds".** Game ticks (100) rather than wall time, so pausing or lag does not split or join runs unexpectedly, and tests are deterministic. Recommendation: accept.
4. **Interleaved events.** "Consecutive" is read per merge key. Mining sand and gravel alternately keeps one run each, rather than breaking both into single rows. Recommendation: accept.
5. **Profession changes and raids are polled** (every 100 and 20 ticks), because NeoForge 21.1 has no events for them. A villager's first sighting each session is only a baseline, so a change while it was unloaded, or before the world opened, is missed. Recommendation: accept, and note the limit in the tool description if live checks show confusion.
6. **Container transfers are net diffs** per open/close session, by item id. Hopper movement while a chest is open is attributed to the player. Components are ignored, so a renamed sword and a plain one count together. Recommendation: accept for v2.
7. **Notes store both** the model's concise `text` and the verbatim `playerWords` (the question that produced the note), plus the conversation and request ids. A note made during a steering message records the turn's original question, not the steering text. The origin is data, not yet a clickable chat link. Recommendation: accept; a link to the chat turn can come with the Stage 5 prompt work if it proves useful.
8. **`forget_note` is a hard delete.** A saved link to a forgotten note reports unavailable. Recommendation: accept; there is no undo requirement.
9. **Count-only overflow rows** are returned as entries without positions, and make area searches `PARTIAL`. Recommendation: accept; the alternative, hiding them, would present absence as proof.
10. **Session gaps** (game time advancing between sessions without recording) and the journal's start time make overlapping searches `PARTIAL`. An unfiltered search stays `COMPLETE` but always states "recording since". Recommendation: accept, so that every result is not marked partial.
11. **Place links reuse Stage 3's marker.** `journal-place` stays a journal-owned target id, because `PackSageTools` requires a record's targets to share its provider. It draws with Stage 3's `world-place` marker when that has landed. Recommendation: accept; if Stage 3 changes the marker's API, adapt `JournalNavigation.Client` only.
