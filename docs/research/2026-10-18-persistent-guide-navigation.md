# Persistent guide and quest navigation

Date: 2026-10-18.

Scope: targeted source inspection for saved destinations that survive client reloads in the same world. Durable navigation is separate from model-facing evidence handles. A destination is only a locator; the active world, provider, target existence, access and visibility must be checked again when the player clicks. Ponder API details are cross-checked against the [official Ponder 1.0.82+mc1.21.1 artifact](https://maven.createmod.net/net/createmod/ponder/ponder-neoforge/1.0.82%2Bmc1.21.1/) and [upstream Ponder source](https://github.com/Creators-of-Create/Ponder/tree/mc1.21.1/dev).

The parallel [JEI investigation](2026-10-18-persistent-jei-navigation.md) establishes the category-plus-canonical-ID policy used by the [combined specification](../specs/2026-10-18-persistent-navigation.md). The JEI questions below describe this guide-focused investigation's boundary; the implementation uses that companion report's unique-ID resolution and rejects recipes without a reliable durable identity.

## Current flow and coupling

`Evidence.NavigationTarget` carries `(scope, providerId, sourceHandle, targetId)`. `ConversationStore` persists all four values. `ChatContracts.Evidence` and `Turn` require every target to match a source by scope, provider and source handle. `AssistantRuntime.navigate` also requires the target and its source in the current view, then calls `KnowledgeService.refreshNavigation`.

`KnowledgeService.refreshNavigation` currently GETs the provider using the old `sourceHandle`, requires one record with that exact source handle and exact old target among its targets, then authorizes the refreshed target. This preserves the existing historical-reference contract but makes the saved link depend on an evidence identity that can include a process-local query/snapshot generation. `open` checks the target is among the service's bounded refreshed-navigation authorization set before dispatching to the provider. The final provider `open` methods perform their own scope and current-target checks.

The common evidence handles are query-scoped concepts: JEI viewer handles include runtime generation and snapshot version (`PackSageJeiPlugin`), and Ponder candidate IDs use the current registration's one-based ordinal plus `System.identityHashCode` (`PonderGuideReader`). In contrast, the chat serialization stores historical scopes containing `providerRuntime` and `requestGeneration`. These values must be rebound to the active scope after the runtime has established same-world, writable-session and late-completion checks.

Currently generated in-game navigation providers are `jei`, `patchouli`, `ftb_quests`, and `ponder`; web URLs use provider `web` and a separate validated external-navigation path. Native recipe-plan records wrap evidence handles but retain the underlying provider and `targetId` (`NativeProvider`), so the destination value can survive that wrapper even when the source handle cannot.

## Stable locator assessment

| Provider | Existing destination material | Reload stability from source | Revalidation needed |
|---|---|---|---|
| Ponder | Component ResourceLocation, e.g. `create:mechanical_press` | Stable component ID. Do not save registration ordinal/hash or scene candidate ID. `PonderUI.of(ResourceLocation)` is the public component viewer entry point; inspected API exposes no public single-scene-ID factory. | On current client registry, find at least one registration whose component exactly equals the parsed destination; open the component viewer on the client thread. A removed component is unavailable. Multiple storyboards for one component intentionally resolve to the same component viewer. |
| FTB Quests | Quest code ID; current targets use the same canonical value for source and target (`FtbProvider`, e.g. `1000000000000002`) | Stable independently of snapshot, and current live-file `open` already resolves the parsed ID against the current quest file. | Retain the existing active-scope, client-thread, current quest-file identity and exact canonical ID checks. Current code already rejects an absent quest. |
| Patchouli | Book ID + entry ID + display page. Current source is `book#entry`; target adds `#page@lifecycle=N`. | Book/entry/page form a durable locator; the lifecycle suffix is explicitly transient. It can be stripped while decoding legacy saved targets, without the old source handle, because target ID contains book and entry too. | Re-resolve current loaded book and entry; require visible, unlocked entry and a current unlocked/display page. Preserve page bounds, current scope, client executor, and lifecycle rechecks during open. Current `PatchouliProvider.open` already implements these access checks but rejects a lifecycle mismatch before resolution. |
| JEI | Current target duplicates `viewerHandle`; canonical recipe ID can be null for opaque/generated entries. Viewer handle includes runtime and query snapshot identity. | Not generally stable. For projections with a canonical recipe ID, that ID may be a migration candidate, but it may resolve to multiple categories/recipes and current code does not define a unique saved viewer destination. Opaque and generated projections have no demonstrated durable key. | Requires provider-specific design for a canonical recipe destination and ambiguity policy. Do not assume that stripping `jei/<generation>/<snapshot>/` preserves identity. |
| web | Validated URL in both source and target | Durable URL text, but still untrusted saved data. | Keep current scheme/host validation and external open path; it is not a local adapter resolver. |

Ponder API evidence for this scope matches the existing [Ponder compatibility research](2026-10-18-ponder-api.md): the official source/artifact exposes a component viewer, not an exact-scene deep link. Describe the destination as the Ponder viewer for a component, not a scene deep link.

## Minimal contract recommendation

Use the already persisted `NavigationTarget.targetId` as the provider-specific destination key; do not require its historical `sourceHandle` to resolve that destination. Keep the source handle as the citation/attribution anchor bound to the historical turn, and keep model-facing evidence handles unchanged for `read_evidence`. No new turn field or conversation schema is needed for this migration. The active runtime should retain its existing current-conversation membership, read-only-world, current-world/scope epoch, selection and asynchronous completion guards.

Add an adapter resolver hook with a default implementation that preserves current exact old-GET behavior for providers not yet migrated. The resolver receives the saved target plus active `Evidence.Scope`, revalidates `targetId` against current provider state, and returns a fresh current-scope `NavigationTarget` (or unavailable/stale). `KnowledgeService` authorizes only that freshly resolved target and keeps the existing bounded authorization set and provider `open` call. The runtime validates the historical target/source pair before resolution, then does not require the fresh handle to appear in the current view. `GuideDocumentProvider` can implement the hook by scheduling on its client executor and delegating to a narrow `GuideDocumentReader` destination resolver; the default reader behavior remains unsupported. This gives Ponder a minimal resolver based on current component registration without requiring the old candidate handle. Scope equality, current presence, access/visibility checks, and click-only opening remain mandatory.

Existing saved values are sufficient for narrow migrations: FTB uses `targetId` directly; Patchouli can parse the book, entry and page from `targetId` and discard only `@lifecycle=N`; Ponder legacy `targetId` is already the component ID even though `sourceHandle` is ephemeral. Do not migrate JEI destinations until unique stable identity and ambiguity behavior are specified. Resolution must not create `read_evidence` handles or mark them as current model observations.

## Focused validation seams

- `PonderGuideReaderTest`: resolve a saved component after recreating/reordering registrations and changing ordinal/hash identities; open when any current registration has the component; reject absent component, malformed ID, wrong provider and off-client-thread open. Multiple registrations sharing a component must remain a component-viewer destination, not arbitrarily select one scene.
- `GuideDocumentProviderTest`: resolver executes through the client executor, uses the current scope, preserves the default unsupported behavior, and returns no target after component removal. `KnowledgeServiceTest`: a destination resolves without the original source handle, but a mismatched provider/scope or late active-scope change cannot authorize it; opened targets still pass the bounded authorization gate.
- `PatchouliProviderTest`: old lifecycle suffix is ignored only during destination migration; current open still rejects hidden/locked/missing entries, locked/missing pages, malformed IDs and wrong scope. Exercise page opening after a lifecycle increment.
- `FtbProviderTest`: saved quest destination opens after provider snapshot/runtime recreation when the same canonical quest ID exists, and fails after removal or current file/scope change.
- `ConversationStoreTest` and `AssistantRuntimeTest`: destination survives save/load and can be used by a follow-up or restored conversation in the same world without a fresh model evidence handle; other-world read-only state, new-world invalidation, new-chat/selection invalidation and late resolver completion remain rejected. Existing exact source-bound targets should remain readable during migration.
- `JeiProjectionTest`: the companion JEI investigation defines canonical recipe/category identity and duplicate/opaque behavior. Add restart survival for that defined identity; existing viewer-handle snapshot invalidation tests continue to cover temporary navigation.

## Evidence limits

This is source/API research, not installed live acceptance. It does not establish whether all third-party Ponder component registrations are safe to enumerate at click time, nor whether every Patchouli book/page ID remains stable across a modpack update. In those cases, current existence and access checks prevent stale or unauthorized opening; they do not guarantee a historical link still exists after content changes. JEI durable identity remains underspecified and should be scoped separately. Work on Ponder/FTB/Patchouli remains bounded if the shared persisted-destination contract and resolver failure statuses are chosen; broader universal migration remains bounded only after JEI's identity policy is decided.
