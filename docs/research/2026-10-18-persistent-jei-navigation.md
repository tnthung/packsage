# Persistent JEI navigation research

Date: 2026-10-18.

## Question and scope

This research evaluates whether saved PackSage recipe links can navigate after a JEI runtime restart while keeping evidence `sourceHandle` values runtime-local. It covers the current PackSage navigation path, JEI 19.27.0.340 API capabilities, stable identifier candidates, ambiguity and visibility handling, and the existing test seams. It does not select a wider navigation architecture.

## Findings

### Current PackSage path

- `JeiProvider.toRecord` currently creates every recipe target with `sourceHandle == targetId == projection.viewerHandle`; the viewer handle embeds runtime generation, snapshot version, category ID, and either canonical ID plus ordinal or an object-identity fallback. See [`JeiProvider.java`](../../src/main/java/dev/packsage/knowledge/jei/JeiProvider.java).
- `PackSageJeiPlugin.RuntimeState` retains `viewerHandle -> RegisteredRecipe(category object, recipe object, scope, output focus)` in a map capped at 512 entries. A new runtime creates a new state; closing a runtime clears that map. An exact GET using an unretained `jei/...` handle returns unavailable. Retained reads revalidate category and recipe membership, then freshly project the current layout and visibility. See [`PackSageJeiPlugin.java`](../../src/main/java/dev/packsage/knowledge/jei/PackSageJeiPlugin.java), especially `RuntimeState.snapshot`, `MAX_NAVIGATION_REGISTRATIONS`, and `showRecipe`.
- `KnowledgeService.refreshNavigation` currently issues an exact GET using the saved target's old `sourceHandle`, requires the returned record to have that same source handle, and authorizes the old target. Its `open` then delegates to the provider. Therefore the service cannot reach a provider's stable-ID resolver through today's flow. See [`KnowledgeService.java`](../../src/main/java/dev/packsage/knowledge/KnowledgeService.java) `refreshNavigation` and `open`.
- The 2026-10-14 JEI navigation refresh plan explicitly scoped its fix to runtime-retained handles and deferred cross-restart IDs. See [`2026-10-14-jei-navigation-refresh.md`](../plans/2026-10-14-jei-navigation-refresh.md).

### JEI 19.27.0.340 API evidence

The local Gradle cache contains JEI 19.57 artifacts, not the pinned 19.27 sources. I inspected the exact 19.27.0.340 `jei-1.21.1-common-api` source archive from the maintainer's Maven repository; the listing identifies the archive and version. The exact game file/version is also listed by [CurseForge](https://www.curseforge.com/minecraft/mc-mods/jei/files/7420585/additional-files).

- `IRecipeCategory.getRecipeType().getUid()` provides the category's `ResourceLocation` UID. `IRecipeCategory.getRegistryName(recipe)` is nullable and defaults to `RecipeHolder.id()`; categories may override it. Thus a JEI recipe can lack a canonical ID, and PackSage's current extraction only attempts IDs for `minecraft:` categories even though the API permits custom category overrides.
- `IRecipeManager.getRecipeType(uid)` returns an optional category type. `getRecipeCategory(type)` resolves its current category. `createRecipeLookup(type).get()` supplies current recipe objects; `limitFocus(...)` can preserve the existing output-item focus, and `includeHidden()` exists. The lookup API has no direct canonical-ID index, so a resolver must inspect returned recipes and call the category's `getRegistryName`.
- `IRecipesGui.showRecipes(category, recipes, focuses)` opens the supplied exact recipe object; `showTypes(...)` opens a category. This supports exact navigation after a restart by resolving the current object from the current manager, without persisting Java objects.
- The API documents category UID as unique identification for a recipe category and `RecipeType` equality as UID plus recipe class. Still, resolution should verify that the current category lookup yields one matching registered category and reject ambiguity rather than assuming current data is clean.

Primary API source artifact: [JEI 19.27.0.340 common API sources](https://maven.blamejared.com/mezz/jei/jei-1.21.1-common-api/19.27.0.340/jei-1.21.1-common-api-19.27.0.340-sources.jar). Relevant entries are `mezz/jei/api/recipe/category/IRecipeCategory.java`, `mezz/jei/api/recipe/IRecipeManager.java`, `mezz/jei/api/recipe/IRecipeLookup.java`, `mezz/jei/api/recipe/RecipeType.java`, and `mezz/jei/api/runtime/IRecipesGui.java`. The artifact directory lists the source archive and exact version at [the Maven version index](https://maven.blamejared.com/mezz/jei/jei-1.21.1-common-api/19.27.0.340/).

### Stable target and resolution implications

- Minimal new target ID candidate: `recipe-v1|<categoryUid>|<canonicalRecipeId>`. Both components are Minecraft `ResourceLocation` strings, whose allowed namespace/path syntax excludes `|`, making this a simple unambiguous, versioned encoding. Parse each component with strict `ResourceLocation` validation and require canonical round-trip text. Keep `sourceHandle` in its current ephemeral form for exact evidence reads and record identity.
- On a fresh runtime, parse the target ID; resolve exactly one category by UID, enumerate that category's current recipe lookup under the shared work budget (saved targets do not currently carry an output focus), and compare the category's current `getRegistryName(recipe)` to the canonical ID. Require exactly one matching recipe. Zero means unavailable; more than one means ambiguous and stale/unavailable. Do not use an ordinal or object identity as a tie-breaker.
- Re-run current category/recipe/ingredient visibility checks before emitting the refreshed record or opening it. Current projection code can return unknown visibility and rejects hidden/unknown recipes during retained-handle GET. Stable resolution should preserve those checks. An opaque semantic projection may still have a canonical JEI registry ID: opaque means PackSage cannot decode category slots, not that JEI cannot identify the recipe.
- If `getRegistryName` is null or throws, no API-guaranteed unique recipe-level ID is available. Do not persist a class-name, identity-hash, list index, output-item-only substitute, or projection fingerprint as an exact destination: the API does not guarantee such derived values uniquely identify a registered recipe, and PackSage ingredient projections can be partial or opaque. A category-only `category-v1|<categoryUid>` target could open `showTypes`, but that changes a recipe link into a category link and is a separate product requirement. Recommend marking such recipe links non-persistent until a supported stable ID exists; categories that override `getRegistryName` remain eligible even when PackSage semantic projection is opaque.
- Existing canonical runtime handles can be migrated when reopened if their embedded category and canonical ID can be recovered and the current JEI registry resolves a unique match. The old ordinal is not a durable identity. Because ResourceLocation paths may contain `/`, parse legacy handles against the current bounded set of category UIDs and accept only one category-prefix interpretation plus a unique canonical recipe match; reject malformed or ambiguous legacy handles. Legacy handles with only an object-identity fallback have no safe migration.

### Shared navigation resolver seam

The proposed provider hook is the necessary seam. A default `KnowledgeProvider.refreshNavigation(target, scope)` can preserve today's exact-old-handle GET/binding behavior for all providers. JEI can override it to resolve its stable `targetId`, freshly project one current record, and return that record's fresh navigation target. `KnowledgeService` then validates that the scope and provider still match, the resolution was backed by exactly one fresh matching recipe record/target, and the requested stable destination was preserved before adding only the resolved current target to its existing bounded authorization set. It must not require the fresh `sourceHandle` to equal the saved handle. The subsequent `open` can keep using the fresh target's ephemeral handle, which the same live runtime has just registered.

This hook should not turn the old handle into evidence or widen model evidence authorization: it is only a current-provider navigation revalidation path. For a legacy saved handle, the JEI override may resolve the parsed stable identity and return a new current target; for malformed or unresolved handles it returns no target. Keeping the default implementation means non-JEI providers retain exact source binding.

### Bounds and test seams

- JEI capture already uses `MAX_CATEGORIES = 256`, `MAX_SCANNED_RECIPES = 2048`, `MAX_CURSOR_SEEK = 65_536`, `MAX_PAGE = 64`, and a shared `DocumentBudget`; retained navigation is capped at 512. Exact stable lookup must use explicit bounds as well. Within a single category it can stop after the second match (ambiguity established), but absence proof requires exhausting the bounded lookup. If the category recipe stream exceeds the chosen navigation cap before a match or exhaustion, report unavailable/partial; never guess from an incomplete search.
- `JeiProjectionTest` has strong local seams: dynamic proxies implement `IRecipeManager`, `IRecipeLookup`, `IRecipeCategoriesLookup`, categories and runtime; `AtomicReference` lists can model add/remove/replace and recipe IDs; visibility proxies can hide recipes; `IRecipesGui.showRecipes` captures the opened recipe. Existing assertions cover fresh exact reads, stale/unretained handles, bounded category/recipe scans, hidden recipes/categories, removal/replacement and navigation source-handle mismatch.
- A restart regression can create a second runtime/plugin state over the same fake current category and recipe list, then refresh/open using only the saved stable target. Assert the new source handle differs by generation/version, the exact current recipe object is shown, and duplicate/missing/null-ID/hidden targets fail closed. A category with an overridden `getRegistryName` and opaque projection should also demonstrate that opaque semantics do not block identity-based navigation.
- `KnowledgeServiceTest` currently tests the generic provider `query(GET)` refresh and exact source binding. Add focused default-hook compatibility and stable-provider migration checks there if the common resolver contract is adopted; this test seam can prove that authorization stores only the current returned target and rejects provider/scope/destination substitution.

## Evidence, inference, and open requirement

**Direct evidence:** the PackSage behavior above comes from current source and tests; the listed method signatures and `getRegistryName` default come from the exact 19.27.0.340 API source archive. **Inference:** category UID plus non-null canonical recipe ID is a practical stable locator across runtime restarts because JEI exposes current recipe lookup and exact display APIs. It is conditional on registry data preserving the ID and uniqueness. **Unknown:** whether PackSage should save category-only navigation for opaque recipes/categories, and what precise scan budget should govern resolution in a very large category. The exact ID resolver remains bounded if it uses the shared document budget and rejects inconclusive scans. Recipes without a non-null JEI registry name have no evidence-backed exact persistent identity in the current API contract.

The exploration remains bounded for a minimal stable-ID implementation. The provider resolver and shared service hook preserve the existing lifecycle boundary. Escalation is only needed if the product requires navigation for recipes without JEI IDs, fallback to category pages, or best-effort selection when duplicate IDs occur; those requirements have no safe source-defined answer.

## Live follow-up: navigation work budget

The 2026-10-18 installed test used JEI 19.64.0.455. A saved legacy torch handle parsed correctly and found `minecraft:torch` in `minecraft:crafting`, but the first implementation rejected it after 2,048 recipes because another entry remained. The complete current crafting category contained 2,963 recipes. The failure was the identity scan allowance, not recipe removal, malformed migration or an exhausted semantic extraction budget.

Navigation now allows at most 65,536 recipe identity/membership checks, with a shared `DocumentBudget.callback(JeiProvider.ID, MAX_NAVIGATION_RECIPES)` allowance. This applies both to canonical-ID resolution and the later retained-object membership check during opening. The separate 2,048 semantic-value budget, 256-category bound, visibility checks and duplicate rejection remain. An incomplete category scan still fails closed; exactly 65,536 entries is supported. Shared accounting also bounds multi-handle evidence reads rather than multiplying the allowance for every handle.

Temporary instrumentation measured the 2,963-recipe resolution at 77.3436 ms on the first click after restarting Minecraft and 13.1021 ms on a later legacy-link click. Both opened the native torch recipe. These are individual live observations, not a latency guarantee for arbitrary categories or mod callbacks. A synchronous navigation-specific allowance is the contained correction; introducing scan continuations across ticks would require additional registry-lifetime and cancellation handling and was not justified by these measurements. The instrumentation was removed after diagnosis. See the [validation record](../validation/2026-10-18-persistent-navigation.md) for the installed artifact and acceptance boundaries.
