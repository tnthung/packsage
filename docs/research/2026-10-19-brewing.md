# Brewing API evidence

Date: 2026-10-19.

Scope: the approved [brewing extension](../specs/2026-10-19-brewing.md). Source inspection establishes contracts, not installed acceptance.

The project pins Minecraft 1.21.1 and NeoForge 21.1.202 in `gradle.properties`. The generated `build/moddev/artifacts/neoforge-21.1.202-sources.jar` contains the full mapped Minecraft and NeoForge source used for this inspection; the NeoForge module-only sources in the Gradle cache omit vanilla classes.

## Live source and enumeration

- `net/minecraft/world/level/Level.java` exposes `public abstract PotionBrewing potionBrewing()`.
- `net/minecraft/world/item/alchemy/PotionBrewing.java` owns private `containers`, `potionMixes` and `containerMixes` lists. Vanilla rows are `Mix<T>(Holder<T> from, Ingredient ingredient, Holder<T> to)` records. The container list determines supported bottle inputs and is separate from the conversion lists.
- `PotionBrewing.getRecipes()` returns custom `IBrewingRecipe` entries only, explicitly excluding vanilla potion and container mixes. Reading only that method misses vanilla brewing.
- The current `mix(reagent, bottle)` checks custom recipes first, then vanilla container conversions, then vanilla potion conversions. List order is meaningful. Container conversion retains the potion holder; potion conversion retains the bottle item and changes the potion holder.
- `net/neoforged/neoforge/common/brewing/BrewingRecipe.java` has public `getInput()`, `getIngredient()` and `getOutput()` getters over declarative fields. Its output includes stack count and components. Subclasses can override behavior, so decoding this schema does not establish arbitrary subclass semantics.
- `IBrewingRecipe` exposes executable input/ingredient/output methods, not an enumerable declarative contract. Unknown implementations require a verified decoder and must remain opaque. No broad item-by-item probing is needed for the approved reader.

## Batch semantics

`net/minecraft/world/level/block/entity/BrewingStandBlockEntity.java` uses slots 0 through 2 for bottles, 3 for reagent and 4 for fuel. Starting an operation consumes one fuel unit; blaze powder supplies 20 units. Finishing invokes the brewing mix for each bottle slot and shrinks the reagent once, retaining its crafting-remainder behavior. The ordinary brew duration is 400 ticks.

A transformation's one output stack does not establish one reagent per bottle. Up to three bottle slots share an operation; arbitrary custom outputs may have other stack counts. Evidence and planning must preserve this limit rather than publishing fabricated crafting totals.

## Existing PackSage seams

`NativeRecipeReader` currently reads ordinary recipe-manager entries; `NativeProvider` routes discovery, evidence and current bounded planner reads through it. `Evidence.RecipePayload` already carries component-distinct input/output stacks and constraints. The public `plan_recipe` target remains an item ID, so a named potion variant cannot be requested exactly. Unknown quantities and batch constraints must keep those plans partial.
