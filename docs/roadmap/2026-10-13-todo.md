# PackSage tool roadmap

Updated: 2026-10-15.

Organize work by actual tool signature, then target/filter/result changes, then adapter coverage. Player behavior determines what each tool does; textual behavior categories are not the top-level roadmap structure. The [behavior-driven tool design](../specs/2026-10-14-behavior-driven-tools.md) defines the completed tool contracts and common execution rules.

Headings below are the final tool signatures. They summarize named JSON arguments, not positional APIs; a question mark denotes an optional or nullable argument. Implementation history is separate from the target contract.

Checked items record delivered backing capabilities within their stated limits; installed acceptance is tracked in the [validation record](../validation/2026-10-14-behavior-driven-toolbox.md). Unchecked items track work toward the final contract. Completion status does not narrow the intended behavior. Keep one logical mod identity across version-specific implementations; every final read follows the fresh-per-call rule.

## Suggested order

1. Implement `search_inventory(target, filter?, cursor?, limit?)`, including registered target dispatch, provider-owned search and live reads on every call.
2. Fill its observed adapter gaps: Pocket Storage, Curios and entity inventories. Verify opened-menu live access and each target's actual data path.
3. Replace broad pack discovery with `search_document(...)`, `search_recipe(...)` and `search_registry(...)`; extend their references through `read_evidence(handles)` and `read_progress(handles)`.
4. Extend `plan_recipe(identity, quantity, depth?)` only for verified recipe semantics. Add narrower provider coverage when real play needs it.
5. Supply authorized server-only evidence behind these same tools where client access is insufficient. Apply fresh-per-call migration to every existing tool family.

## `search_inventory(target, filter?, cursor?, limit?)`

Target: enumerate or filter one live inventory selected through player, opened, item, targeted block/entity or ridden access.

Player examples: “What am I carrying?”, “Find iron in this chest”, “What is in my backpack?”, “What is this donkey carrying?” and “Do I have logs in this storage system?”

Use one operation, `search_inventory(target, filter?, cursor?, limit?)`. No filter enumerates the selected inventory; a filter narrows the same contents. Equipment and cargo are inventory sections. Selectors resolve the inventory owner and live access path on every call. Full selector, filter, result and freshness rules live in the [design](../specs/2026-10-14-behavior-driven-tools.md).

### Contract and dispatch

- [x] Introduce a shared `Toolbox` interface whose default methods return `NotHandled`, and register adapter instances. Matching lives inside each operation implementation; the dispatcher tries adapters in order, continues only on `NotHandled`, and stops on success or any other error. Adding an adapter requires no dispatcher changes.
- [x] Replace model-facing `read_inventory`, `read_storage` and current player-only `search_inventory` with the unified target/filter contract; update schema, dispatch, grounding and tests together.
- [x] Collect target schemas from registered adapters and expose available types instead of a closed target list. Schemas describe inputs; they do not select handlers. Native selectors include `player`, `opened`, `targeted`, `ridden` and `item`; adapters can add their own types.
- [x] Pass the complete query, including filters and pagination, through the adapter chain. Adapters resolve and match shared item/menu/world selectors internally; reuse live resolution utilities where appropriate.
- [x] Enumerate without a filter and apply the same optional name, ID, tag, tooltip and section filters across supported targets.
- [x] Read current contents on every call, including repeated queries and reference-based reads; return unavailable when live access is lost instead of falling back to saved contents.
- [x] Return inventory ownership, observed sections, counts, each call's read time and coverage consistently; expose reusable references only for resolvable locations.
- [x] Replace snapshot pagination with bounded live reads; cursors retain only continuation information and never frozen result pages.
- [x] Distinguish empty contents, no filter matches, empty hand selection and unavailable contents. Missing selected fields or unread sections cannot establish absence.

- [ ] Result normalization preserves component-distinct item variants, including provider aggregates; report unavailable variant detail.

- Search item names

- Search item registry IDs

- Apply filters to any supported target
  - [x] Shared filters — apply the common filter semantics across supported targets, including section selection and explicit missing-field coverage.
  - [ ] Adapter query execution — prefer each provider's own live search and paging; allow cheap equivalent filtering without cloning a network, building a parallel index or scanning the whole system for a bounded result.
- Page search results

Every query and continuation reads current data, revalidates its target and applies the same filter semantics. Pages read at different times do not establish one consistent inventory state. Adapters use their owning sources; selected fields or bounded candidate coverage cannot be silently treated as complete absence.

## Implementation history

The legacy public inventory signatures were read_inventory, player-only search_inventory and read_storage; broad discovery used search_pack. Their backing readers and tests are migration inputs, not limits on the final operations.

The old opened shortcut captured data before closing a menu, `read_evidence` replayed observed record bodies, and inventory/storage cursors retained result pages. These behaviors are replaced by live access, source locators and per-call reads.

Historical delivered pagination check (not a final-contract acceptance check):

  - [x] Shared inventory search — bounded results and immutable continuation pages for vanilla player inventory/equipment.
