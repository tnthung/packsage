# PackSage feature roadmap

Updated: 2026-10-14.

Organize work by feature, then operation, then mod/framework. Each checkbox represents support for one operation in one implementation. Checked items describe delivered capabilities within their stated limits; unchecked items are planned work, not compatibility claims.

Group equivalent queries and results regardless of internal APIs, payload formats or access providers. Distinct questions and coverage guarantees remain separate tasks even when they share a tool.

Keep model-facing tools organized by capability. Mod-specific and version-specific readers implement those shared interfaces; the model should not need a different calling convention for each mod. Storage already has a common tool and reader interface, but automatic selection among future mod readers remains implementation work.

Keep one logical mod ID and one adapter-status entry across version-specific implementations. A mod can appear under several features below without becoming several status entries. Verify each reader's data access and supported versions before implementation.

## Suggested order

1. Fill observed inventory gaps: Pocket Storage display contents, Curios equipment, and specialized storage readers needed during real play.
2. Expand shared documentation coverage: Modonomicon, GuideME, then Create/Ponder.
3. Add acquisition and mechanic readers: JER, Just Enough Professions, Just Enough Breeding, then Just Enough Effect Descriptions.
4. Add narrower manuals, multiblock readers, pack scripts and alternative quest systems where the installed pack needs them.
5. Add the optional server companion for facts unavailable to a client-only reader. Features requiring server access depend on a verified access path.

## Inventory and equipment

- Read inventory and equipment slots
  - [x] Minecraft — occupied hotbar, main inventory, armor and offhand slots.
  - [ ] Curios — equipped accessory slots for Relics, Artifacts and other participating mods.
- Expose held-slot selection
  - [x] Minecraft — selected hotbar and offhand slot references, including empty slots.
- Expose addressable slot references
  - [x] Shared inventory/equipment reader contract — scoped per-observation references; vanilla player slots are implemented.

Vanilla inventory records identify selected roles and reusable slot references. Fresh storage reads revalidate the observed stack before reading; empty hand selections remain distinct from occupied items. Item-specific abilities and progression are separate features below.

## Inventory search

- Search item names
  - [x] Shared inventory search — localized and custom item names in vanilla player inventory/equipment.
- Search item registry IDs
  - [x] Shared inventory search — namespaced item identities in vanilla player inventory/equipment.
- Search item tags
  - [x] Shared inventory search — synchronized tag membership in vanilla player inventory/equipment.
- Search tooltip text
  - [x] Shared inventory search — bounded available item-instance tooltip lines in vanilla player inventory/equipment.
- Select inventory sources
  - [ ] Shared inventory search — player slots, equipment and accessible storage observations or networks.
- Page search results
  - [x] Shared inventory search — bounded results and immutable continuation pages for vanilla player inventory/equipment.

Provide one model-facing `search_inventory` query contract across supported readers. Backends translate the common filters into their own access mechanisms; adding a storage mod should not add another model tool or query syntax. Results identify the owning inventory/network, reusable slot reference where applicable, item count, observation time and coverage. Unavailable sources or missing searchable fields remain explicit, so no matches in partial data do not prove an item is absent.

Search applies to owned or accessible contents; `search_pack` remains the tool for installed-pack knowledge. Current `search_inventory` supports selected name, ID, tag and tooltip fields for vanilla player slots; additional inventory/storage sources remain planned. `read_inventory` retains exact item-ID filters, while `read_storage` has literal name/ID text filtering. Missing selected fields and metadata/output bounds remain explicit partial coverage.

## Storage

- Read opened contents
  - [x] Minecraft — visible non-player slots from standard container menus, with partial coverage.
  - [ ] Pocket Storage — entries from the custom storage display.
  - [ ] Sophisticated Backpacks — opened backpack contents.
  - [ ] Sophisticated Storage — opened storage-block contents.
  - [ ] Applied Energistics 2 — item entries displayed in an opened terminal.
  - [ ] Refined Storage — item entries displayed in an opened terminal.
  - [ ] Mekanism — contents exposed by an opened storage menu.
- Read storage through an item at an observed slot
  - [x] Minecraft — direct synchronized container and bundle contents at an observed vanilla player inventory/equipment slot.
  - [ ] Pocket Storage — supported synchronized storage-item data.
  - [ ] Sophisticated Backpacks — backpack contents at a supported inventory or equipment slot.
  - [ ] Sophisticated Storage — storage-block item contents at an observed slot.
  - [ ] Functional Storage — stored contents of a drawer item at an observed slot.
  - [ ] Storage Drawers — stored contents of a drawer item at an observed slot.
  - [ ] Mekanism — storage-item contents at an observed slot.
  - [ ] Applied Energistics 2 — network contents through a usable wireless terminal in an inventory or equipment slot.
  - [ ] Refined Storage — network contents through a usable wireless terminal in an inventory or equipment slot.
- Read targeted contents
  - [ ] Minecraft — closed containers through authorized server access.
  - [ ] Sophisticated Backpacks — placed backpacks when their data is available.
  - [ ] Sophisticated Storage — storage blocks when their data is available.
  - [ ] Functional Storage — drawer item quantities when their data is available.
  - [ ] Storage Drawers — drawer item quantities when their data is available.
  - [ ] Applied Energistics 2 — local storage-block contents when their data is available.
  - [ ] Refined Storage — local storage-block contents when their data is available.
  - [ ] Mekanism — storage blocks when their data is available.
- Read complete connected-network item totals
  - [ ] Applied Energistics 2 — supported authorized network access.
  - [ ] Refined Storage — supported authorized network access.

Use the same `read_storage` contract for item containers and wireless terminals, selecting a reader from the item at the supplied slot reference. Results identify whether the source is local item contents or a connected network and report coverage. Inventory inspection and search provide those references; mainhand and offhand are convenient slot selectors, not separate storage capabilities. Revalidate the referenced slot before a fresh read so a moved or replaced item is not mistaken for the original target. A reader should require holding only when the mod's actual access rules require it.

Opened observations are partial visible views, not complete network totals. A wireless terminal can be an access candidate without being held; reading its network still depends on the provider's connection, permission, power and range requirements. Targeted and network readers require a verified access path.

Pocket Storage's opened-display feature addresses the eight entries missed by the current generic menu reader in the ATM10 trial.
