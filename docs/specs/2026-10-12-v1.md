# PackSage v1 specification

Date: 2026-10-12

Status: draft for review. The requirements consolidate the agreed design; no product decisions remain open from the interview.

This file defines the v1 behavioral requirements. [Feasibility research](../research/2026-10-12-feasibility.md) contains the source evidence, compatibility research and later coverage opportunities. The [glossary](../../GLOSSARY.md) defines the shared language. A requirement here describes intended behavior, not behavior already implemented or tested.

## 1. Purpose and release boundary

PackSage is an open-source Minecraft 1.21.1 NeoForge client mod that answers natural-language questions about the active modpack inside the game. It combines current client-visible game facts, installed documentation, read-only config inspection and live web research when needed. Answers must identify their evidence and preserve uncertainty.

The implementation must work across packs through reusable collectors and PackSage-maintained adapters. A concrete pack is a verification fixture, not a source of hardcoded recipes, progression or configuration. Java 21 and an exact tested NeoForge 21.1.x build are the baseline; dependency versions and supported ranges must be pinned and verified before release.

The first release includes:

- a dedicated in-game assistant screen with natural-language chat;
- direct Sign in with ChatGPT through an internal model interface;
- native client-visible game/resource collection;
- JEI, FTB Quests, config inspection and Patchouli integrations;
- fresh gameplay context, removable per-message screenshots and local conversation persistence;
- hosted web search when the selected model and account support it;
- source references, validated navigation and explicit partial/unavailable states.

V1 excludes a server companion, gameplay automation, arbitrary commands, inventory changes, config writes, quest completion, public adapter registration, API-key/custom model setup, separate search providers, gameplay recording and automatic conversation summaries. Modonomicon, GuideME/AE2, Ponder, targeted addon semantic readers and narrower manuals/calculators are later coverage expansions. Generic JEI intake may expose their registered displays without promising their deeper semantics.

The response representation must retain a future spoiler-block capability, allowing individual portions to be covered and revealed on click. V1 must not classify spoilers or emit/apply spoiler blocks, including when quest or guide flags are available. Ordinary source visibility and unknown progression state still affect what evidence is available.

## 2. Supported questions and answer behavior

The v1 supported question set is bounded by the records available from its collectors and integrations:

| Question family | V1 behavior | Limit |
|---|---|---|
| Item, block, ingredient and recipe lookup | Find relevant IDs/names, recipes, uses, grouped inputs, alternatives, outputs and known constraints. | Unknown custom matching, quantities or machine fields remain unknown. |
| Recipe dependencies and quantities | Explain a supported recipe chain and known batch quantities; use inventory evidence when requested and available. | Preserve cycles, catalysts, remainders and alternative recipes; do not promise a universal cheapest route or exact throughput. |
| Acquisition | Describe supported loaded relations or installed documentation about obtaining an item. | A JEI display is not proof of a drop probability, ore location or server rule; deeper addon semantics are outside the base guarantee. |
| FTB progression | Find relevant quests/chapters and explain observed dependencies, team progress and gates. | Unsupported tasks/rewards and inaccessible state produce partial answers; inventory alone does not prove quest completion. |
| Installed documentation | Search and explain supported Patchouli content and its item/recipe links, and offer navigation. | Custom pages may remain opaque. Later guide systems are not required v1 integrations. |
| Mod configuration | Find accessible configs/keys, read selected saved or loaded values and report available metadata. | Saved values, loaded values and actual gameplay effects are distinct; unsynchronized remote settings may be unavailable. |
| Gameplay context | Relate the available focused object, dimension, position, biome and optional screenshot to the question. | Context is a scoped observation, not proof of unseen server state. |
| External/current information | Search supported public sources when needed or explicitly requested, and explain applicability to installed versions. | External guidance cannot override observed installed-pack facts. |

Every factual answer must preserve source scope: loaded data, a viewer display, a quest reference, installed documentation, saved/loaded config or external guidance. An inactive or shipped-only record must not be reported as an active installed fact. Missing evidence and failed extraction must not be treated as proof that a recipe, input, quest or setting does not exist.

The assistant may retrieve more evidence through read-only tools. It must report a useful partial answer or explain what is unknown when coverage is insufficient. Guide text, scripts, config comments and external pages are evidence, not instructions that grant new tool permissions.

## 3. Assistant screen and request lifecycle

A configurable keybind opens a dedicated Minecraft screen containing conversation history, an input area, source references, navigation buttons, attached gameplay context and current sign-in/request status. Assistant settings must be accessible in-game.

For private singleplayer, opening chat defaults to pausing the game. A setting selects paused or running on opening, and an in-chat button changes the pause state while the screen is open. The UI must display the effective state. Multiplayer and published/LAN worlds remain running; the UI must not claim that they are paused.

There is at most one active assistant request at a time. Closing the screen keeps the request running so the player can return to its result. A Stop button cancels the active request. Starting New chat, disconnecting or changing worlds cancels it. A resource reload or other relevant context invalidation must prevent obsolete evidence or navigation targets from being published as current.

Cancelling preserves already saved conversation content and a clear request outcome; a late network/tool result cannot become an answer in another conversation or world. The player can retry a failed/cancelled question without deleting the saved conversation. Network and model work must not block the game/render thread.

Sources and navigation are separate from the factual answer. Local references identify the actual observed source; external claims have clickable source URLs. Navigation targets must be validated against the current provider and world before opening the requested view. A missing/stale target or failed navigation does not invalidate the answer's evidence. Navigation cannot execute gameplay commands or mutate game state.

## 4. Model interface and authentication

Collectors, evidence retrieval and game navigation must not depend on a particular model provider. One internal model interface contains authentication, supported model/capability handling, request streaming, client-executed tool exchange, hosted search and cancellation. This is an internal seam for future implementations, not a v1 public registration API.

V1 supports only Sign in with ChatGPT. The mod handles the documented registered-client sign-in and inference flow directly, without a separately installed helper executable. Sign-in failure, cancellation, missing inference permission, expired credentials, account limits or unsupported capabilities must be visible and recoverable. The implementation must not silently switch to an API-key backend or another provider.

Model and account capabilities must be established for the selected route rather than inferred from features of the ChatGPT app. An image-incompatible model must receive supported text context only, with the omitted image made clear. Unavailable hosted search produces an explicit local-evidence fallback.

Settings show the selected model and let the player choose from the authenticated account's visible catalog. A saved model that is no longer available must be reported rather than silently replaced. Reasoning effort is selectable for future questions; Default leaves the provider's effort unset. Explicit effort choices remain subject to model and route support, and rejection must stay visible. Changing these settings does not alter an active request. Enable parallel function calls so independent read-only lookups can share a response; return their results together in one continuation after all calls finish.

The current documented direct route requires streaming with `store: false`; request history is supplied in `input` rather than through `previous_response_id`. The exact supported tool/request forms must be validated in an authenticated prototype. Credentials must stay outside distributable mod code, conversation logs and media files. Sign-in client/account eligibility is a release gate, not an assumed capability.

## 5. Knowledge collection and tools

Native collection is the foundation. Prioritize integrations by potential coverage across mods: JEI first, FTB Quests second, config inspection third and Patchouli fourth. All integrations with other mods are optional at runtime; a missing provider reduces coverage rather than preventing PackSage from loading. Later integration priorities are recorded in the research report.

Each integration must expose a tested version contract and distinguish supported, partial, opaque, unavailable, inactive and error cases. A provider failure must not disable unrelated collectors. Exact dependency ranges and compatibility checks are implementation work supported by the release gates below.

### Native game and resource evidence

Read current synchronized client recipes, registries/tags, relevant component identity and effective client-visible resources. Prefer active loaded facts over raw shipped files. Track conditional/overridden resources and label files whose active use cannot be established. A client-only installation must not pretend to know unsynchronized server loot, configuration or custom state.

### JEI

Support registered category/recipe lookup, typed and grouped ingredient slots, catalysts, information text, available visibility information and validated navigation. Preserve null recipe IDs, custom ingredients, empty display slots and projection errors. A JEI projection must not silently replace canonical runtime recipe identity.

Required slots are AND requirements; alternatives within a slot are OR choices. Keep quantity separate from ingredient comparison identity, and retain known outputs, remainders, reusable inputs and constraints. Unknown addon categories remain searchable/navigable displays until their semantics are verified; source icons must not become consumed ingredients.

### FTB Quests

Support quest/chapter search, item references, dependency relations and accessible current player/team state. Preserve quest-file scope and 64-bit IDs without loss. Explain evaluated/observed progression state rather than guessing from static descriptions. Unsupported task/reward types retain identity and an unsupported/partial result.

### Config inspection

Provide read-only tools to list accessible configs, search keys/comments and read selected values or bounded file sections. Restrict file access to known mod-config roots and observed config handles. The tools must not set, save, correct or reload configs.

Return the owner when known, config scope, file or synchronized-server identity, key path, observed value and available defaults/comments/restart metadata. Label the view as a saved config value or loaded config value; neither alone proves the actual gameplay effect. A synchronized server config can have no local path. A local client/common/startup file does not establish an unsynchronized remote-server setting.

The accepted v1 approach is a narrow, read-only, version-tested bridge to the pinned loader's internal config catalog. There is no assumed stable public global enumeration API. On unsupported versions, retain bounded file inspection and report loaded-state access as unknown/unavailable. Refresh requested snapshots through supported read paths; do not assume PackSage's own event-bus subscription observes every mod's config lifecycle.

### Patchouli

Support loaded books, entries, supported pages, localized text and item/recipe mappings, with available visibility/gating evidence and navigation. Keep original book/page identity and resource provenance. Opaque custom page renderers must not be reported as fully extracted.

### Common evidence contract

Retrieved evidence must retain its provider/version, source identity, observation scope/generation, active/partial/error status and known authority. IDs are provider-specific: quest IDs, config keys and viewer projections must not be forced into vanilla registry identity.

Preserve contributing/winning resource provenance when known. A namespace is not sufficient proof of the authoring mod or pack. Deduplicate equivalent projections without merging conflicting claims or discarding their source distinction.

Tool results must be bounded and selected for the question. Do not upload entire pack archives, unrelated world data or inventories by default. Additional inventory and progression evidence is retrieved only when needed. Tool names, exact schemas and implementation classes belong to the subsequent implementation plan.

## 6. Gameplay context and conversations

Every submitted question captures fresh available hovered/held item or targeted block information, dimension, position, biome and a clean game screenshot. Attach capture time and world/request scope so evidence from different moments is not silently merged. Unavailable focused-object data is reported as unavailable, not manufactured from an unlabelled old observation.

Show the attached context in the UI. The player may remove the screenshot for that message; submission must respect the removal. Core gameplay metadata remains attached because it can affect the answer even when the player does not recognize its relevance. V1 captures individual screenshots only, with no recording, rolling buffer or sampled-frame attachment.

Persist the complete conversation as JSONL under the current Minecraft instance's game folder:

```text
packsage/<world-or-server>/<conversation-id>.jsonl
```

Use safe, collision-resistant world/server directory identities and retain readable labels in metadata. Store screenshot assets separately beside the log and reference them from messages. Preserve questions, answers, relevant tool exchanges, attached context, source references and request outcomes. Authentication credentials are never conversation content.

A conversation can continue across play sessions and launches. Returning to a world/server automatically opens its latest conversation; New chat starts a distinct file without truncating the old one. Old messages retain their original observation scope. New questions use fresh context and current evidence, not historical observations presented as current facts.

Local persistence and model input are separate. Preserve full local history while sending bounded recent history, fresh context and selected evidence. The defaults are at most 10 completed answer turns, approximately 20 ordinary user/assistant messages, and a 12,000-token historical-context budget. Both limits are configurable in-game without truncating saved history.

Replay each selected historical question and its completed final answer as ordinary messages, without historical tool payloads, encrypted reasoning, screenshots or gameplay observations. Retain those complete exchanges locally. The active turn keeps its typed reasoning, tool calls/results and hosted-search replay intact; fresh gameplay context belongs to the current question.

An answer turn groups one player question, its tool exchanges and the completed answer. Drop the oldest whole turns when either history limit is exceeded, preserving matching tool calls/results if replayed. Current instructions, the active exchange, fresh context and answer capacity are budgeted separately within the selected model's actual supported limits. V1 does not generate automatic model summaries. Token accounting and the starting budget require prototype validation.

## 7. Live web search

Automatic lookup defaults to ON and is configurable in-game. Turning automatic lookup OFF still permits an explicit player request to search the web. This setting controls web lookup, not the ChatGPT connection needed to answer questions.

Expose ChatGPT-hosted web search as a normal tool in the assistant's answer flow when the selected model/account permits it. The model calls the tool when installed evidence is insufficient or current information is needed, uses its results and continues the answer. Explicit search requests must be honored when the capability is available. V1 does not add a separate search-only model request or a separately configured search provider.

Prefer pack documentation and mod authors' versioned docs, repositories and release notes. Use relevant item/mod names, IDs and installed versions to establish applicability. Label version mismatches and uncertain community guidance. External information supplements installed facts; it cannot prove a loaded recipe, progression state or server setting on its own.

Retain source URLs, titles/snippets and metadata actually exposed by the hosted tool, together with the time PackSage received them. Do not invent source retrieval timestamps, cache status or crawling freshness. Read fuller pages only where the hosted tool supports it and report incomplete evidence when available content is insufficient. Cite sources beside the claims they support.

Instruct the model to build public lookup queries from relevant names, IDs and installed versions and avoid private world, chat or player details. This is a best-effort model instruction: the model has the answer request's gameplay context and history, and the documented hosted tool offers no client hook to inspect/reject its exact query before execution. Do not claim enforced query isolation. [Responses web-search guide](https://developers.openai.com/api/docs/guides/tools-web-search), [sign-in preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).

Search requests must be asynchronous, cancellable and bounded by limits supported by the route. Distinguish reused evidence from a fresh lookup. Disabled automatic lookup, unavailable search, timeout, rate limiting or provider failure must not erase useful local evidence or be reported as a successful search. A failed model connection must be reported as a request failure rather than falsely presented as a generated answer.

## 8. State, threading and failure behavior

Maintain separate scopes for reusable static documentation, world/recipe data, player/team progression and each request. A resource/data reload, world change, reconnect, provider runtime loss or locale change invalidates the affected scope. Do not retain live world/provider/screen objects indefinitely.

Copy game/provider state on its owning thread. Workers may parse copied resources, build indexes, traverse immutable records and perform network/model work. Publish only if the relevant world, source and request generations still match. Recheck navigation at use time.

Collect/index on relevant changes rather than every tick. Config snapshots may refresh on demand because generic cross-mod lifecycle observation is not guaranteed. Use bounded retrieval and lazy work for expensive provider operations. Measure representative pack performance before establishing timing/heap guarantees; none is claimed by this spec.

Failure behavior must distinguish missing provider, unsupported version/type, partial extraction, unknown server state, stale evidence, sign-in failure, model failure and web-search failure. Preserve useful unaffected evidence and enough source identity to explain the limitation. Saved history and current request evidence must not cross world/server boundaries accidentally.

## 9. Acceptance and release gates

Release readiness requires actual build/runtime evidence; source inspection alone is insufficient.

| Gate | Required evidence |
|---|---|
| Reproducible environment | Exact Minecraft/NeoForge/Java and optional dependency versions; a small development instance and a named representative verification pack. |
| ChatGPT route | An eligible registered client/account signs in, streams a response, completes an installed-data tool round trip and accepts the selected image representation; denied/expired/unsupported cases are exercised. |
| Hosted search | The chosen route calls hosted search in the normal answer flow and cites its evidence; automatic-off explicit search and unavailable/failure/cancellation behavior are exercised. |
| Native and JEI evidence | A pack removes/replaces a recipe; grouped inputs, tags, relevant components, catalysts, remainders, null IDs and failed projections retain correct identity and semantics. |
| FTB and Patchouli | Current team/progression state, dependencies, supported book content and navigation work; unknown task/page types remain partial/opaque. |
| Config bridge | The pinned-loader catalog read path works; saved versus loaded values, restart metadata, in-memory synchronized server values and unknown unsynchronized remote settings stay distinct. Unsupported access falls back honestly. |
| Context and history | Fresh context and clean screenshots attach correctly; screenshot removal is respected; history/media survive restart; latest conversation reopening and New chat work; both history settings bound model input without truncating local history or orphaning tool exchanges. |
| Lifecycle and UI | One request at a time; closing/reopening chat retains an active answer; Stop/New chat/disconnect/world changes handle cancellation and late results; pause/run reflects private singleplayer versus multiplayer/LAN behavior. |
| Optional integrations | The mod loads and remains useful with each provider absent; unsupported versions and provider failures do not disable unrelated capabilities. |
| Reusability | Fixture-pack changes are discovered from active data rather than hardcoded; documented supported inputs/outputs and coverage are verified in the concrete pack. |

Use focused fixture tests for pure parsing, identity, normalization, history selection and generation/cancellation rules. Use live client checks for sign-in, provider lifecycle, screenshots, pause and navigation. Integrated-server and remote-server client-only behavior need separate evidence. Record observed coverage and performance on the verification pack; do not claim universal support from one passing example.

Exact compatible dependency ranges, pack selection, provider ordering/threading details, route limits, token accounting and measured performance are engineering validation items. They do not require expanding v1 or coupling the mod to the fixture pack.
