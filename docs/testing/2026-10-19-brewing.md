# Brewing player checks

Date: 2026-10-19.

Use a singleplayer fixture with the newly built PackSage JAR installed through the normal closed-instance copying workflow. These checks establish installed behavior separately from the [automated validation](../validation/2026-10-19-brewing.md). The agent runs Java, Gradle and automated tests.

1. Ask how to brew a potion of Strength in the loaded pack. Inspect the executed recipe searches and citations. The answer should use current brewing evidence and identify the input potion, reagent and resulting potion, retaining any pack-specific or incomplete-rule limits.
2. Ask how to make that potion a splash potion, then a lingering potion. Check that each conversion preserves the potion contents and changes the bottle type. Compare with the loaded brewing/JEI display where available.
3. Ask about the ordinary, extended-duration and stronger versions available in the pack. The returned records must distinguish potion components rather than collapsing them into one `minecraft:potion` result. Unsupported variants must not be invented.
4. Ask whether three bottles need three reagents. The answer should distinguish a transformation from a brewing operation, which can share one reagent across up to three bottle slots. It must not present an ordinary per-bottle crafting tally as the exact brewing cost.
5. Ask for a bounded brewing plan and inspect the reported constraints. Item-ID targeting does not choose a named potion variant, and unresolved batch/fuel/custom rules must keep the plan partial.
6. Where a supported mod contributes a declarative NeoForge brewing recipe, compare its declared input, reagent, output count and components with fresh evidence. Other custom implementations should remain explicitly opaque rather than appear absent or be executed to guess their rules.

Record the actual artifact hash, profile, questions, tool/evidence observations and remaining limits in the validation document. A successful answer does not establish that a brewing operation was performed, that every custom implementation is supported or that client rules match a remote server.
